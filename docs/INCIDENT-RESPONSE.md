# Terra Nova — נוהל תגובה לאירוע אבטחה

**עודכן:** 21 בספטמבר 2026
**מצב:** טיוטה תפעולית. **לא נבדקה על ידי עורך דין ולא תורגלה.**

> החובות המשפטיות בעת אירוע — למי מדווחים, תוך כמה זמן, ובאילו נסיבות — טעונות בדיקה
> של עורך דין, לרבות לאור תיקון 13. המסמך הזה מתאר את **הצד ההנדסי**: מה לעשות
> במערכת, באיזה סדר, ואיך לא להשמיד ראיות בדרך.

## שלב 0 — לפני שנוגעים בכלום (0–15 דקות)

**אל תמחקו ואל תאתחלו לפני שאספתם.** אתחול שרת מוחק לוגים בזיכרון, מאפס את המגביל,
ובמקרים רבים משמיד בדיוק את מה שנדרש כדי להבין מה קרה.

1. **רשמו את השעה** ומי דיווח.
2. **שמרו לוגים** — ייצוא מלא מהספק לטווח הרלוונטי, לאחסון נפרד.
3. **צלמו מסך** לכל ראיה שעלולה להיעלם.
4. **שמרו `AuditLog`** — `SELECT * FROM "AuditLog" WHERE "createdAt" > ...` לקובץ.
5. **אל תשנו קוד עדיין.**

## שלב 1 — בלימה (15–60 דקות)

לפי סוג האירוע:

**דליפת מידע / השתלטות על חשבון**
1. החליפו `AUTH_SECRET` — **מנתק את כל הסשנים מיד**, כולל של התוקף.
2. אפסו סיסמאות לחשבונות שנחשדים כנפגעים.
3. אם נחשפו מפתחות אחסון — החליפו `STORAGE_*` והנפיקו מפתחות חדשים.

**פגיעה בתשלומים**
1. העבירו ל-`PAYMENT_PROVIDER=manual` — הזמנות נרשמות ואינן מסומנות שולם אוטומטית.
2. החליפו `PAYMENT_WEBHOOK_SECRET`. **ללא סוד כל callback נדחה** — זו ברירת מחדל בטוחה.
3. צרו קשר עם ספק הסליקה.

**הזרקת קוד**
1. גלגלו לגרסה תקינה ידועה.
2. השוו את `package-lock.json` מול commit תקין.
3. הריצו `npm audit` ובדקו שינויים לא מוכרים.

**זמינות**
1. הפעילו הגנת DDoS אצל הספק.
2. הדקו את דליי הקצב זמנית.

## שלב 2 — הערכה (1–4 שעות)

ענו על השאלות, בכתב:

| שאלה | היכן בודקים |
| --- | --- |
| מה נחשף? | `AuditLog`, לוגי גישה, לוגי המסד |
| כמה נפגעים? | שאילתה על הטווח |
| **האם נחשפו תמונות חדרים?** | לוגי האחסון — מפתחות שנקראו |
| האם נחשפו סיסמאות? | רק hash של bcrypt; לא ניתנות לשחזור, אך יש לאפס |
| האם נחשפו פרטי אשראי? | **לא אמור להיות אפשרי** — אינם נשמרים. אם כן, זהו אירוע מסוג אחר לגמרי |
| מתי התחיל? | הרשומה המוקדמת ביותר |
| האם עדיין פעיל? | תעבורה בזמן אמת |

## שלב 3 — הודעה

⚖️ **החובה, המועד והנמענים — לבדיקת עורך דין.** אין להסתמך על המסמך הזה.

מה שכן ידוע הנדסית: יש בידינו את הנתונים הדרושים לזיהוי הנפגעים — `Order.email`,
`User.email`, ובעלי עיצובים שמורים.

הודעה ללקוח צריכה לכלול, בעברית פשוטה: מה קרה, מתי, איזה מידע שלו, מה עשינו, מה מומלץ
שיעשה, ואיך לפנות אלינו. **אין להמעיט בחומרה ואין להבטיח מה שלא ניתן לקיים.**

---

## שלב 4 — תיקון ושחזור

1. תקנו את השורש, לא את הסימפטום.
2. הוסיפו בדיקה אוטומטית שנכשלת על הבאג — אירוע ללא בדיקת רגרסיה יחזור.
3. שחזרו מגיבוי אם נדרש. ⚠️ **הגיבוי אינו מוגדר בפרויקט ולא תורגל שחזור.**
4. אשרו שהשירות תקין: `npm run qa` ו-`npm run test:e2e`.
5. החזירו את ההגדרות הזמניות למקומן.
