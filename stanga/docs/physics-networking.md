# פיזיקה ברשת — מה באמת קורה

## השורה התחתונה

השרת מריץ את הסימולציה. הלקוח מריץ **את אותה סימולציה** כניבוי, במצב שבו היא
אינה מחליטה דבר. **אין rollback ואין replay** — המסמך הזה קיים כדי לומר את זה
במפורש ולהסביר למה.

## למה הלקוח מריץ פיזיקה בכלל

כדי שלחיצה על מקש תזיז את השחקן באותו פריים. אם הלקוח היה מצייר רק snapshots
מהשרת, כל צעד היה מגיע באיחור של RTT שלם.

אפשר היה לנבא רק את תנועת השחקן המקומי, בלי פיזיקה — אבל זה היה דורש מימוש
שני של קוד התנועה, שהיה נפרד מהשרת עם הזמן. זה בדיוק מה שהארכיטקטורה הזו
נבנתה כדי למנוע.

## למה אין rollback

Rollback קלאסי דורש לשמור את מצב הפיזיקה בטיק מסוים ולהריץ אותו מחדש. מצב
Havok אינו ניתן לסריאליזציה מהדפדפן, ולכן לא ניתן לשמור אותו ולהחזיר אותו.
במקום זה הלקוח סוגר את הפער באופן רציף.

זו פשרה אמיתית, לא פתרון מושלם: ברשת גרועה מאוד ייתכנו תיקונים מורגשים.

## איך נסגר הפער

| מה           | איך                                                                |
| ------------ | ------------------------------------------------------------------ |
| השחקן המקומי | הזזה של 15% מהשגיאה בכל טיק (`PlayerBody.nudge`, שומרת על המהירות) |
| היריב        | השגיאה מוזרקת ל־`PlayerCommand` שלו — הוא "מתכוון" לחזור למקום     |
| הכדור        | תיקון מהירות: מהירות השרת ועוד משיכה למיקום השרת                   |
| כל השלושה    | קפיצה מיידית מעל סף (2.5 מ׳ / 3 מ׳ / 2 מ׳), ובכל פתיחה מחדש        |

תיקון היריב דרך הפקודה הוא ההבדל המהותי: הוא נשאר **בתוך** הפיזיקה — מתנגש,
נחסם ונדחף כמו כל שחקן — במקום לעבור דרכה פעמיים בשנייה.

## מה הלקוח לא מחליט

`MatchEngine` מקבל `rules: 'mirrored'` במשחק אונליין. במצב הזה הוא עדיין מריץ
תנועה, בעיטות, חטיפות ושליטה בכדור — אבל **אינו** בודק את קו השער, אינו צובר
נקודות ואינו מקדם שלבים. הניקוד, השעון, השלב והפתיחות מועתקים מה־snapshot,
והשערים מגיעים כאירועי שרת.

התוצאה: צליל בעיטה נשמע מיד (ניבוי), ושער נספר רק כשהשרת אמר שהוא שער.
אם ניבוי של פגיעה בקורה היה שגוי, המחיר הוא צליל מיותר — לא נקודה מיותרת.

## תדירויות

| מה              | קצב                                    |
| --------------- | -------------------------------------- |
| טיק סימולציה    | 60 לשנייה                              |
| patch מצב ללקוח | 20 לשנייה                              |
| קלט מהלקוח      | עד 90 לשנייה, טיק אחד נצרך בכל טיק שרת |
| ping            | כל 2 שניות                             |

הקלט נצרך אחד לטיק. אם חבילה מאחרת, דגלי־מצב (כיוון, ריצה, החזקת בעיטה)
נשמרים ודגלי־קצה (בעיטה, חטיפה) לעולם אינם חוזרים על עצמם.

## שני באגים שהבדיקה הזו חשפה

שניהם היו קיימים כבר מהשלבים החד־שחקניים, ורק הרצת השרת מסקריפט גילתה אותם:

1. **`reset()` ירה גופים במקום להציב אותם.** ל־Havok אין קריאת teleport;
   `setTargetTransform` נותן לגוף **מהירות** לעבר היעד. לכן כל פתיחה מחדש
   שיגרה את הכדור לעבר המרכז במקום להניח אותו שם. כעת `PhysicsWorld.teleport`
   מדליק את סנכרון ה־pre-step לצעד אחד בלבד — זהו ה־teleport האמיתי היחיד.
2. **סיוע השליטה בכדור ביטל בעיטות.** הוא קרא את `MatchState.ball.velocity`,
   שמתעדכן רק אחרי צעד הפיזיקה, ולכן בתוך הטיק שבעט הוא עדיין קרא אפס — וכתב
   את האפס הזה בחזרה. כעת הוא קורא את המהירות החיה מהגוף.
