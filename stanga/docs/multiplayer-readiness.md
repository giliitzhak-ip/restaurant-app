# מוכנות למשחק רשת סמכותי

מסמך זה מתאר מה כבר בנוי נכון עבור אונליין, ומה יוחלף כאשר יתווסף שרת סמכותי.
**בגרסה 0.2.0 עדיין אין שום קוד רשת** — אין שרת, אין סוקטים, אין prediction ואין rollback.
המטרה כאן היא שהמעבר לא ידרוש כתיבה מחדש של הסימולציה.

## העיקרון

```
Controller  →  PlayerCommand  →  MatchSession  →  סימולציה בצעד קבוע  →  MatchState  →  רינדור
```

הסימולציה אינה יודעת מאיפה הגיעו הפקודות, והרינדור אינו יכול לשנות את המצב.
זהו בדיוק הגבול שעליו יושב שרת סמכותי.

## מה שלב ב׳ שינה — וזה השינוי המשמעותי ביותר לקראת האונליין

בגרסה 0.1.0 היה שחקן אנושי אחד, והקלט שלו היה מחובר קשיח לסימולציה.
בגרסה 0.2.0 הוצג המבנה שהשלב הבא בנוי עליו:

```ts
interface PlayerSlot {
  playerId: string;
  team: TeamId;
  name: string;
  colorId: number;
  controller: PlayerController; // ← נקודת ההחלפה
}
```

`MatchSession` מחזיק רשימת slots ובכל טיק קורא ל־`controller.poll()` של כל אחד
מהם. שלושת המצבים הם **אותו קוד בדיוק**, ונבדלים רק בתוכן הרשימה:

| מצב                          | slots                        |
| ---------------------------- | ---------------------------- |
| נגד המחשב                    | `[Human, AI]`                |
| שני שחקנים מקומי             | `[Human, Human]`             |
| **אונליין 1 נגד 1 (שלב ג׳)** | `[Human, NetworkController]` |

כלומר: **מצב האונליין כבר לא דורש שינוי בסימולציה, ב־UI או בחוקים.**
הוא דורש מימוש של `PlayerController` אחד נוסף, ושרת שמחזיק את `MatchState`.

## חוזה הפקודה

`PlayerCommand` (ב־`src/input/PlayerCommand.ts`) הוא מבנה שטוח, סריאליזבילי
במלואו, ובלי שום הפניה למנוע:

```ts
interface PlayerCommand {
  tickId: number; // הטיק שאליו הפקודה שייכת
  sequenceNumber: number; // מונה עולה לכל controller — לסידור ולמניעת כפילויות ברשת
  playerId: string;
  moveX: number;
  moveY: number; // וקטור תנועה במרחב העולם
  aimX: number;
  aimY: number; // וקטור כיוון במרחב העולם; אפס = שמור כיוון
  sprintPressed: boolean;
  shootPressed: boolean; // קצה — טיק אחד
  shootHeld: boolean; // מצב
  shootReleased: boolean; // קצה — טיק אחד
  tacklePressed: boolean; // קצה — טיק אחד
  lobToggle: boolean; // קצה — בקשת החלפה, לא מצב
}
```

שתי החלטות כאן נועדו במפורש לרשת:

1. **הווקטורים הם במרחב העולם, לא יחסית למצלמה.** ההמרה נעשית ב־Controller
   בצד הלקוח, ולכן שרת אינו צריך לדעת דבר על המצלמה של אף שחקן.
2. **`lobToggle` הוא בקשה ולא מצב.** סוג הבעיטה חי ב־`PlayerState` ולכן הוא חלק
   מהמצב הסמכותי. לקוח אינו יכול "להצהיר" שהוא בועט מוגבה — הוא רק מבקש להחליף,
   והשרת מחליט.

| AI כצרכן פקודות      | `src/ai/AIController.ts`                              | היריב אינו נוגע במנוע: הוא מייצר `InputCommand`. שחקן מרוחק יתפוס את מקומו ללא שינוי בסימולציה.                 |

| קונפיגורציה אחת      | `src/config/GameConfig.ts`                            | שרת ולקוח חייבים להסכים על כל מספר. הם ייבאו את אותו קובץ.                                                      |

## מה עדיין לא מוכן, ומה יוחלף

| נושא                        | מצב היום         | מה יידרש                                                          |
| --------------------------- | ---------------- | ----------------------------------------------------------------- |
| בעלות על המצב               | הלקוח הוא הסמכות | השרת יחזיק את `MatchState` ויהיה המקור היחיד לאמת                 |
| תחבורה                      | אין              | WebSocket או WebRTC DataChannel, עם קצב שליחה נפרד מקצב הסימולציה |
| דטרמיניזם של הפיזיקה        | **לא מובטח**     | ראו להלן — זו המשוכה האמיתית                                      |
| prediction ו־reconciliation | אין              | חיץ פקודות בלקוח, replay של טיקים מאושרים                         |
| השהיית רשת                  | אין              | interpolation buffer, וסיבוכי קצב שעון                            |
| אנטי־צ׳יט                   | אין              | אימות פקודות בצד השרת (הפקודות כבר מוגבלות לתחום תקין)            |

## המכשול האמיתי: דטרמיניזם של Havok

הסימולציה מתקדמת בצעד קבוע, אך **Havok שרץ ב־WebAssembly אינו מבטיח תוצאה זהה
ביט־בביט בין מכשירים**. לכן לא ניתן להסתמך על lockstep דטרמיניסטי בין לקוחות.

שלוש דרכים אפשריות, לפי סדר העדפה:

1. **שרת סמכותי שמריץ את אותה פיזיקה ב־Node** ומשדר snapshots.
   הלקוחות מבצעים interpolation. זו הדרך הפשוטה והבטוחה, והארכיטקטורה הנוכחית תומכת בה כמעט כמו שהיא.
2. **שרת סמכותי עם prediction בלקוח** עבור השחקן המקומי בלבד, ותיקון כאשר ה־snapshot סותר.
   דורש `MatchState` הניתן לשחזור — קיים — ואת היכולת להריץ מחדש טיקים מתוך חיץ הפקודות.
3. **Lockstep דטרמיניסטי** — לא מומלץ כל עוד הפיזיקה היא Havok/WASM.

## נקודות החיבור המדויקות

- `Game.simulate()` (`src/core/Game.ts`) הוא המקום היחיד שאוסף פקודות ומקדם טיק.
  בגרסת רשת הוא יקבל פקודות מהחיץ המקומי ומהרשת במקום מ־`InputManager` ומ־`AIController`.
- `MatchEngine.submitCommand()` כבר מקבל פקודה לכל שחקן לפי מזהה — זו בדיוק החתימה שדרושה לשרת.
- `MatchEngine.step()` הוא הפונקציה שהשרת יריץ; היא אינה קוראת ל־DOM ואינה תלויה בקצב הרינדור.
- `ScoringSystem` כבר מונע ניקוד כפול לפי `shotId`, כך שהודעת ניקוד כפולה מהרשת לא תיצור נקודות כפולות.

## מה שיש להיזהר ממנו בשלב האונליין

- `MatchEngine` יוצר כיום את גופי הפיזיקה דרך Babylon. לשרת ב־Node תידרש הפרדה של בניית
  הגופים מבניית ה־meshes (היום הן יחד ב־`entities/`).
- חלק מהאפקטים (אודיו, רטט, באנרים) מונעים על ידי אירועי `MatchEngine`. בגרסת רשת יש לוודא
  שהם מופעלים מה־snapshot המאושר ולא מהניחוש המקומי, אחרת יישמע שער שלא קרה.
- `GameConfig` חייב להיות זהה בין שרת ללקוח; כדאי לשדר גרסה שלו ב־handshake.

## מה נדרש ב־`NetworkController` — המימוש היחיד שחסר

```ts
class NetworkController implements PlayerController {
  readonly kind = 'network';
  readonly deviceId: string; // מזהה החיבור המרוחק
  readonly label: string; // שם השחקן המרוחק

  poll(playerId, tickId, context): PlayerCommand {
    // מחזיר את הפקודה שהתקבלה עבור הטיק הזה מהחיץ,
    // או שכפול של האחרונה כאשר חבילה אבדה.
  }

  isConnected(): boolean {
    /* מצב הסוקט */
  }
  reset(): void {
    /* ניקוי החיץ */
  }
}
```

מסך הניתוק והחיבור מחדש שנבנה בשלב ב׳ עבור בקרים יטפל גם בניתוק רשת ללא שינוי:
הוא מגיב ל־`isConnected()` ולא לסוג ההתקן.

## מה עדיין חסר, לפי סדר

1. **תחבורה** — WebSocket או WebRTC DataChannel.
2. **בעלות על המצב** — היום הלקוח הוא הסמכות.
3. **הפרדת גופי פיזיקה מה־meshes** — `entities/` בונה את שניהם יחד; שרת ב־Node
   יצטרך את הגופים בלבד.
4. **prediction ו־reconciliation** — החיץ והמונה קיימים, הלוגיקה לא.
5. **אנטי־צ׳יט** — אימות פקודות בצד השרת.

> **תזכורת שלא השתנתה:** Havok ב־WebAssembly אינו דטרמיניסטי ביט־בביט בין
> מכשירים, ולכן lockstep אינו אפשרי. הדרך הנכונה נשארת שרת סמכותי שמשדר
> snapshots, עם interpolation בלקוח.
