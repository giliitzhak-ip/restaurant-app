# STANGA — תוכנית שלב ג׳ (גרסה 0.3.0)

## המטרה

אונליין 1 נגד 1 אמיתי: שרת סמכותי, חדר פרטי עם קוד וקישור הזמנה,
חיפוש משחק, חיבור מחדש, ו־Docker. בלי לשבור את המצבים הקיימים.

## הגדרת ההיקף

שלב זה **אינו** כולל 2 נגד 2, Party, בוטים, Quick Chat או סטטיסטיקות קבוצתיות.
אלה שייכים לשלב ד׳, והארכיטקטורה כאן נבנית כדי לקבל אותם בלי שכתוב.

## החסם שנבדק ראשון

לפני כל שורת קוד נבדק הדבר היחיד שיכול היה להפיל את כל השלב:
**האם הסימולציה יכולה לרוץ ב־Node ללא דפדפן?**

נבדק בפועל — `@babylonjs/havok` + `NullEngine` + `PhysicsAggregate` עובדים ב־Node
(כדור נופל, מתנגש ברצפה ונעצר). המשמעות: **השרת מריץ את אותו `MatchEngine`
של הלקוח**, ולא מימוש פיזיקה שני שייפרד ממנו עם הזמן.

התנאי היחיד: הפרדת גופי הפיזיקה מהמראה — בדיוק החסם שתועד ב־`multiplayer-readiness.md`.

## החלטות ארכיטקטורה

1. **ליבה משותפת מהיום הראשון.** `BaseOnlineMatchRoom` ו־`MatchConfig` נכתבים
   כך ש־2×2 יהיה תוספת של קונפיגורציה וחדר, לא מערכת שנייה.
   `MatchConfig` כולל כבר `mode`, `maxPlayers`, `playersPerTeam`.
2. **השרת מריץ את `MatchEngine` הקיים**, לא עותק. כל שינוי בחוקים חל על שניהם.
3. **הלקוח אינו מריץ פיזיקה במצב אונליין.** הוא מנבא את תנועת השחקן המקומי
   בלבד, ומצייר את היריב ואת הכדור מתוך אינטרפולציה בין snapshots. זהו לקוח
   שרת־סמכותי סטנדרטי, והוא היחיד שאינו מתפצל מהשרת עם הזמן.
4. **`NetworkController` מממש את `PlayerController`** שנבנה בשלב ב׳ — בדיוק
   נקודת ההחלפה שתוכננה שם.
5. **קוד ההזמנה אינו reconnect token.** שני מזהים נפרדים לחלוטין.
6. **אין state גלובלי בתהליך.** כל מצב חי בחדר, כדי שהוספת Redis ו־scaling
   בהמשך לא תדרוש שכתוב.
