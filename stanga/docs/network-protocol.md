# פרוטוקול הרשת — STANGA 0.4.0

`protocolVersion`: **2**

השינוי מ־1 ל־2: נוספו חדר `stanga_2v2`, ארבע הודעות לקוח (`t`, `s`, `g`, `c`,
`o`), הודעת `h` מהשרת, שדות ב־`NetInput` (כוונת גובה, סיבוב, מסירה, הקפצה),
סטטיסטיקות ב־`NetPlayer`, ו־`lastViolation` ב־`MatchRoomState`. **חוק הנגיעה
האחת** שינה את חוקי הסימולציה עצמם, ולכן לקוח מגרסה 0.3.0 היה מחשב תוצאה
אחרת — זו הסיבה המהותית להעלאת המספר.

כל מה שמתואר כאן מוגדר בקובץ אחד, `src/net/protocol.ts`, שגם הלקוח וגם השרת
מייבאים. אין שני עותקים שיכולים להיפרד זה מזה.

## גרסאות

הלקוח שולח `protocolVersion` בכל הצטרפות. אם הוא אינו זהה לזה של השרת,
ההצטרפות נדחית עם הקוד `protocolMismatch`, והמשחק מציג בעברית:
"הגרסה שלכם ישנה. רעננו את הדף כדי לשחק אונליין."

יש להעלות את המספר בכל שינוי בפורמט ההודעות, בסכמה, או בחוקי הסימולציה
שעלולים לגרום ללקוח ישן לחשב תוצאה אחרת מהשרת.

## הצטרפות

שם החדר נגזר מהמצב: `stanga_1v1` או `stanga_2v2` (`roomNameFor`).

| כוונה    | קריאה                            | מה קורה                             |
| -------- | -------------------------------- | ----------------------------------- |
| `quick`  | `joinOrCreate(<room>, …)`        | מצטרף לחדר ציבורי פנוי, או פותח אחד |
| `create` | `create(<room>, …)`              | פותח חדר פרטי ומקבל קוד הזמנה       |
| `join`   | `GET /invite/:code` → `joinById` | פותר קוד לחדר ומצטרף אליו           |

אפשרויות ההצטרפות: `protocolVersion`, `intent`, `displayName`, `colorId`.
**כל שאר המידע נקבע בשרת**: המושב (`home-1`, `home-2`, `away-1`, `away-2`),
הקבוצה, ה־`slotIndex`, המיקום, הניקוד והסטטיסטיקות.

הצטרפות בקוד הזמנה קובעת גם את המצב: קוד של חדר 1×1 אינו פותח חדר 2×2 ולהפך,
כי הקוד מצביע על חדר קיים שכבר יודע מה הוא.

סיבות דחייה אפשריות: `protocolMismatch`, `roomNotFound`, `roomFull`,
`matchInProgress`, `rateLimited`, `invalidName`.

## הודעות לקוח → שרת

| שם  | תוכן                                   | הגבלה                         |
| --- | -------------------------------------- | ----------------------------- |
| `i` | `NetInput` — קלט של טיק אחד            | 90 לשנייה לכל לקוח            |
| `r` | `{ ready }` — מוכן להתחלה              | תקציב הבקרה (10–12 לשנייה)    |
| `m` | הצבעה למשחק חוזר                       | תקציב הבקרה                   |
| `p` | `{ t }` — מדידת השהיה                  | תקציב הבקרה                   |
| `t` | `{ team }` — **בקשה** למעבר קבוצה      | תקציב הבקרה                   |
| `s` | ערבוב קבוצות (בעל החדר בלבד)           | תקציב הבקרה                   |
| `g` | הצבעת כניעה                            | תקציב הבקרה + cooldown 20 ש׳  |
| `c` | `{ id }` — צ׳אט מהיר מתוך חמישה קבועים | תקציב הבקרה + cooldown 1.5 ש׳ |
| `o` | פתיחת חדר פרטי לחיפוש (בעל החדר בלבד)  | תקציב הבקרה                   |

כל אחת מההודעות האלה היא **בקשה**. השרת בודק מי שלח אותה, באיזה שלב החדר
נמצא ומה מותר עכשיו, ועונה על ידי שינוי המצב — לא על ידי אישור. `t` נדחית
כשהקבוצה מלאה או כשהקבוצות ננעלו; `s` ו־`o` נדחות ממי שאינו בעל החדר; `c`
נדחית לכל ערך שאינו אחד מחמשת המזהים.

### `NetInput`

```ts
{
  n: number; // מספר סידורי
  mx: number; // תנועה, מרחב העולם
  my: number;
  ax: number; // כיוון פנייה
  ay: number;
  va: number; // כוונת גובה, ‎-1..1
  sn: number; // סיבוב מבוקש, ‎-1..1
  pt: number; // slot מועדף למסירה, ‎-1 = "תחליט אתה"
  f: number; // ביטים
}
```

- `n` — מספר סידורי עולה. השרת מאשר את האחרון שצרך ב־`lastInput`.
- `mx`, `my` — כיוון תנועה **במרחב העולם**, בתוך עיגול היחידה. לכן השרת אינו
  צריך לדעת דבר על המצלמה של אף שחקן.
- `ax`, `ay` — כיוון פנייה מבוקש. אורך אפס = "השאר את הכיוון".
- `va` — כמה גבוה מכוונת הבעיטה. רציף, לא מתג: מתג שטוח/מוגבה אינו יכול
  לכוון לקורה.
- `sn` — **בקשת** סיבוב. השרת מחליט כמה סיבוב יוצא בפועל.
- `pt` — **בקשת** יעד מסירה לפי `slotIndex`. השרת בוחר יעד חוקי, ועשוי לבחור
  אחר. אין כאן שום מסלול שבו לקוח מכריע למי הכדור הולך.
- `f` — ביטים: `Sprint`, `ShootPressed`, `ShootHeld`, `ShootReleased`,
  `TacklePressed`, `LobToggle`, `ChipRequested`, `PassPressed`, `PassHeld`,
  `PassReleased`, `JugglePressed`.

השדות עוברים דרך `sanitizeInput` לפני שהם מגיעים לסימולציה: ערך שאינו סופי
נדחה, וקטור ארוך מ־1 מנורמל, `va` ו־`sn` נחתכים ל־‎-1..1, וביטים שאינם
בפרוטוקול נמחקים.

## הודעות שרת → לקוח

| שם  | תוכן                                                              |
| --- | ----------------------------------------------------------------- |
| `w` | `WelcomePayload` — מזהה השחקן, הקבוצה, המצב, קוד ההזמנה, אורך טיק |
| `q` | `{ t, tick }` — תשובה ל־ping, עם הזמן של הלקוח כפי שנשלח          |
| `e` | `NetEvent` — ראו למטה                                             |
| `h` | `NetChat` — `{ playerId, team, id }`. **המשפט עצמו אינו נוסע**    |
| `y` | בקשת סנכרון מחדש                                                  |

`NetEvent.kind` אפשרי: `kick`, `tackle`, `frameHit`, `scored`, `kickoff`,
`matchEnd`, `violation`, `pass`, `juggle`, `botTookOver`, `playerReturned`,
`surrender`, `roomOpened`.

`h` נושא מזהה בלבד; כל לקוח מחפש אותו בטבלה המקומית `QUICK_CHAT`. לקוח שמנסה
לשלוח טקסט חופשי פשוט נדחה, ולכן אין מסלול שבו טקסט של שחקן אחד מגיע למסך של
שחקן אחר.

`WelcomePayload` **אינו** מכיל reconnect token. הטוקן מגיע מ־Colyseus עצמו
(`room.reconnectionToken`), והוא שונה במהותו מקוד ההזמנה: קוד הזמנה נועד
לשיתוף, טוקן הוא הוכחת זהות ואסור לשתף אותו, לכתוב אותו בקישור או ביומן.

## מצב החדר (Colyseus schema)

`MatchRoomState` — ראו `src/net/schema.ts`:

- `stage` — `waitingForPlayers` / `teamSelection` / `readyCheck` / `countdown` /
  `playing` / `goalFreeze` / `reconnectPause` / `finished` / `rematchVote` /
  `disposing`
- `mode`, `playersPerTeam`, `inviteCode`, `isPrivate`, `stageTimer`
- `phase`, `tick`, `elapsed`, `timeRemaining`, `scoreHome`, `scoreAway`,
  `kickoffTeam`
- `players` — `MapSchema<NetPlayer>` **לפי מושב** (`home-1`), לא לפי חיבור.
  מושב שורד ניתוק, וזה בדיוק מה שתקופת החסד צריכה. אין כאן `player1..player4`
  ואין מערך באורך קבוע — הוספת מושב היא הוספת רשומה.
- `ball`, `lastScore`, `lastViolation`

`NetPlayer` נושא גם `team`, `slotIndex`, `isHost`, `ready`, `rematchVote`,
`surrenderVote`, `botControlled`, `departed`, ואת הסטטיסטיקות (`goals`,
`points`, `assists`, `ownGoals`, `shots`, `passes`, `juggles`, `violations`,
`touches`, `tackles`). הסטטיסטיקות נספרות בסימולציה שבשרת ונשלחות; הלקוח
**אינו** סופר אותן בעצמו, כי שני לקוחות שסופרים בנפרד יגיעו למספרים שונים.

`sessionId` לעולם אינו מתפרסם. הוא עניינו של השרת, ואין ללקוח שימוש בזה של
אחר.

מה שלא מסונכרן: meshes, חומרים, פריימים של אנימציה, גופי פיזיקה. הלקוח בונה
את כל אלה מקומית מתוך המספרים האלה.

## HTTP

| נתיב                  | מה מחזיר                                      |
| --------------------- | --------------------------------------------- |
| `GET /health`         | `{ status, protocolVersion, rooms, clients }` |
| `GET /invite/:code`   | `{ roomId }`, או 404 / 400 / 429              |
| `POST /matchmake/...` | מטופל בידי Colyseus עצמו                      |

`/invite` מוגבל ל־30 בקשות לדקה לכל כתובת (`INVITE_LOOKUPS_PER_MINUTE`).
