# פריסה — STANGA 0.3.0

## מה מורכב משני חלקים

1. **הלקוח** — קבצים סטטיים (`npm run build` → `dist/`). אפשר לארח בכל מקום.
2. **השרת הסמכותי** — תהליך Node שמאזין ל־HTTP ול־WebSocket.

שניהם חייבים להסכים על `protocolVersion`, ולכן יש לפרוס אותם יחד.

## משתני סביבה

### שרת

| משתנה                       | ברירת מחדל | משמעות                                            |
| --------------------------- | ---------- | ------------------------------------------------- |
| `PORT`                      | `2567`     | פורט האזנה                                        |
| `HOST`                      | `0.0.0.0`  | כתובת האזנה                                       |
| `ALLOWED_ORIGINS`           | ריק        | רשימת origins מופרדת בפסיקים. **ריק = כל origin** |
| `INVITE_LOOKUPS_PER_MINUTE` | `30`       | תקרת חיפושי קוד לכל כתובת                         |

`ALLOWED_ORIGINS` ריק מתאים לפיתוח בלבד. בייצור יש להגדיר בדיוק את המקורות
שמהם הלקוח מוגש; חיבור WebSocket מ־origin אחר נדחה לפני השדרוג, ובקשות
matchmaking מקבלות כותרות CORS שאינן מאפשרות אותן.

### לקוח (בזמן build בלבד)

| משתנה                 | משמעות                                                             |
| --------------------- | ------------------------------------------------------------------ |
| `STANGA_SERVER_URL`   | כתובת השרת. ריק = אותו origin ב־build, פורט 2567 בפיתוח            |
| `STANGA_NO_PWA=1`     | build ללא service worker (למשל בתוך iframe מוגבל)                  |
| `STANGA_TEST_HOOKS=1` | חושף `window.__stanga` לקריאה בלבד, עבור בדיקות E2E. **לא בייצור** |

אין בפרויקט מפתחות, סודות או טוקנים, ואף אחד מהמשתנים האלה אינו כזה.

## Docker

```bash
docker build -t stanga-server .
docker run -p 2567:2567 -e ALLOWED_ORIGINS=https://example.com stanga-server
```

או:

```bash
ALLOWED_ORIGINS=https://example.com docker compose up
```

**גילוי נאות:** ה־Dockerfile וה־compose נכתבו ונבדקו לוגית, אך לא נבנו בפועל
בסביבה שבה פותח השלב הזה (אין בה daemon של Docker). מה שכן נבדק בפועל: השרת
עולה ומגיש משחקים כשמותקנות **רק** התלויות שאינן dev, בתוספת `tsx` — בדיוק
מה שה־image מתקין. הריצו `docker build` פעם אחת לפני פריסה אמיתית.

## בדיקת חיים

`GET /health` מחזיר `200` ו־
`{ "status": "ok", "protocolVersion": 1, "rooms": n, "clients": n }`.
זהו גם ה־HEALTHCHECK של ה־image וגם מה שה־load balancer צריך לבדוק.

## WSS ו־TLS

התהליך עצמו מדבר HTTP ו־WS רגילים. TLS מסתיים ב־load balancer או ב־reverse
proxy, שצריך:

- להעביר `Upgrade` ו־`Connection` כדי ש־WebSocket יעבוד;
- להגדיר `X-Forwarded-For` (מגבלת הקצב של `/invite` משתמשת בו);
- timeout ל־idle גדול מ־60 שניות, אחרת חיבורי משחק ייקטעו.

דפדפן שמגיש את המשחק ב־HTTPS **לא** יצליח לפתוח `ws://` — במצב כזה
`STANGA_SERVER_URL` חייב להיות `https://…`, והלקוח יפתח `wss://`.

## Sticky sessions — חובה

חדר חי בתהליך אחד. לקוח שמגיע לתהליך אחר לא ימצא אותו.

- הפעילו sticky sessions לפי IP או לפי cookie **לכל התעבורה**, כולל
  `POST /matchmake/...` וגם חיבור ה־WebSocket עצמו.
- ללא זה, שני שחקנים שלוחצים "חיפוש יריב" בו־זמנית עלולים לפתוח שני חדרים
  בשני תהליכים ולא להיפגש לעולם.

## ריבוי תהליכים

ב־0.3.0 המערכת נבדקה **בתהליך אחד**. היא נכתבה כך שלא יהיה צורך בשכתוב:

- מצב המשחק חי בחדר, לא במודול.
- קודי הזמנה חיים ב־Colyseus Presence, לא ב־`Map` גלובלי.
- מגבלות הקצב הן פר־תהליך במכוון — הן מגבילות רק את הקוראים של אותו תהליך.

למעבר למספר תהליכים יש להוסיף `@colyseus/redis-presence` ו־
`@colyseus/redis-driver` ל־`new Server({ presence, driver })`. ה־profile
`redis` ב־`docker-compose.yml` מעלה את Redis לצורך כך.

**זה טרם נבדק.** אל תתייחסו לפריסה מרובת־תהליכים כמוכנה לייצור לפני שהיא
נבדקה בפועל.

## מה עוד לא נבדק

- בניית ה־image (אין Docker בסביבת הפיתוח של השלב).
- Redis presence/driver.
- עומס אמיתי מעבר לשני שחקנים בחדר, ושני חדרים במקביל.
