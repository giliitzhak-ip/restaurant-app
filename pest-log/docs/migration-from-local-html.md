# מעבר מהגרסה המקומית (pest-log.html) למערכת הענן

## ⚠ הבהרה חשובה על מסמך זה

**קובץ `yomen-hadbara.zip` — ובתוכו `README.txt` ו-`pest-log.html` — לא היה
זמין בסביבת הפיתוח.** תיקיית העבודה הכילה פרויקט אחר לגמרי
(`restaurant-app`), וחיפוש בכל הדיסק לא מצא את הקובץ.

**מה המשמעות:**

| נושא | מה נעשה |
| --- | --- |
| עיצוב (שחור/זהב, RTL, נייד) | נבנה לפי התיאור במפרט. **לא הועתק פיקסל-לפיקסל** מהמקור, כי המקור לא נראה. |
| ששת השלבים | נשמרו כשישה שלבים, בחלוקה לוגית לפי הדרישות (ראו להלן). **החלוקה המדויקת במקור אינה ידועה.** |
| הפונקציות הקיימות | כל מה שהמפרט מונה — תבניות, לקוחות, אתרים, תחנות האכלה, תמונות, GPS, ארכיון, חיפוש — קיים. |
| נתוני localStorage | מנגנון ייבוא **סובלני** שמזהה מבנים נפוצים, ולא מניח מבנה יחיד. |

**מה לעשות כשהקובץ המקורי יימסר:** ראו "התאמה למקור" בסוף המסמך.

ולקפיצה לשדה.

## מה שונה מהגרסה המקומית

| נושא | גרסה מקומית | מערכת הענן |
| --- | --- | --- |
| אחסון | `localStorage` בדפדפן אחד | PostgreSQL + IndexedDB מקומי |
| אובדן מידע | ניקוי הדפדפן = הכול אבד | נשמר בשרת, זמין מכל מכשיר |
| כמה משתמשים | מכשיר אחד | כל העסק, עם הפרדה בין עסקים |
| מספור יומנים | ידני / מקומי | עוקב ובלתי חוזר, מובטח במסד |
| נעילת יומן | אין | יומן שהושלם אינו ניתן לשינוי או למחיקה |
| תיקון | עריכה מוחקת את המקור | גרסת תיקון מקושרת; המקור נשמר |
| PDF | לרוב html2canvas (תמונה) | Chromium → PDF וקטורי, טקסט עברי ניתן לחיפוש |
| עבודה ללא קליטה | תלוי בדפדפן | IndexedDB + תור סנכרון עם מפתחות אידמפוטנטיות |
| רשימת תכשירים | 151 תכשירים מוטבעים בקוד | טבלה עם מקור מידע, תאריך אימות, סטטוס ותוקף |

### על 151 התכשירים
המפרט קובע במפורש: "אין להסתמך על הרשימה המובנית של 151 התכשירים כמידע
עדכני וקבוע." לכן **הרשימה לא הועברה כמו שהיא**. במקומה: טבלת `products`
שבה `source_name` ו-`verified_at` הם **שדות חובה**, והממשק מציג אזהרה על
תכשיר שלא אומת או שאינו בתוקף. תכשיר שרישומו בוטל או שתוקפו פג **חוסם**
השלמת יומן.

לטעינת הרשימה מקובץ מאומת:
```bash
npm run import:products -- --file products.csv --org <uuid> \
  --source "מאגר התכשירים הרשמי" --source-url "<url>" --verified-at 2026-09-01 --dry-run
```
`--dry-run` מציג מה ייטען בלי לכתוב. להסרתו כדי לבצע בפועל.

## ייבוא הנתונים מ-localStorage

### איך זה עובד
1. **סריקה** — נסרקים מפתחות ב-`localStorage` שמכילים
   `pest|hadbara|yoman|yomen|הדברה|יומן|log`. נתמכים שלושה מבנים:
   מערך של יומנים, אובייקט בודד, ואוסף ממופתח (`{id: {...}}`).
2. **מיפוי** — שמות מפתחות נפוצים ממופים לשדות המערכת (באנגלית ובעברית):
   `customer_name`/`שם` → `orderer.name`, `city`/`עיר` → `location.city`,
   `date`/`תאריך` → `execution.performedDate`, וכן הלאה.
3. **שדות שלא זוהו לא נמחקים** — הם נשמרים תחת `legacy.unmapped` בתוך
   היומן, ומוצגים בתצוגה המקדימה. אפשר למפות אותם ידנית אחר כך.
4. **תצוגה מקדימה** — לפני כתיבה מוצגת רשימת הרשומות, מה זוהה ומה לא,
   ואפשר לבחור מה לייבא.
5. **מניעת כפילויות** — לכל רשומה טביעת אצבע מהתוכן. רשומה שיובאה בעבר
   מסומנת ומדולגת, וגם כפילויות בתוך אותו ייבוא מסוננות.
6. **ייבוא כטיוטות** — כל רשומה נכנסת כ**טיוטה**, לא כיומן שהושלם. זה
   מכוון: יומן שהושלם מקבל מספר סידורי ונעילה, ואין להעניק אותם לנתונים
   שלא עברו ולידציה.
7. **ביטול (rollback)** — "ביטול הייבוא האחרון" מוחק בדיוק את הטיוטות
   שנוצרו בייבוא האחרון ומנקה את טביעות האצבע, כך שאפשר לייבא שוב.

### חשוב לדעת
- **הנתונים המקוריים ב-localStorage אינם נמחקים.** הייבוא קורא בלבד.
- יש לפתוח את המערכת **מאותו דפדפן ואותו מכשיר** שבהם נעשה שימוש בקובץ
  המקומי — `localStorage` הוא פר-origin ופר-דפדפן.
- אם הקובץ המקומי הוגש מ-`file://` או מ-origin אחר, הדפדפן לא יחלוק את
  אותו `localStorage`. במקרה כזה: לפתוח את `pest-log.html` באותו דפדפן,
  להריץ בקונסול `JSON.stringify(localStorage)`, לשמור לקובץ, ולייבא אותו
  דרך המסלול הידני (ראו למטה).
- זו **הנקודה היחידה במערכת שקוראת מ-localStorage**. כלל ESLint
  (`no-restricted-globals` + `no-restricted-properties`) חוסם שימוש
  ב-`localStorage` בכל שאר הקוד, כדי שלא יהפוך בטעות למסד הנתונים.

### ייבוא ידני מקובץ JSON
אם ה-`localStorage` אינו נגיש מהדפדפן שבו פתוחה המערכת:
```js
// בקונסול של הדפדפן שבו פתוח pest-log.html:
copy(JSON.stringify(localStorage))
```
לשמור לקובץ, ואז להדביק את התוכן ל-`localStorage` של המערכת החדשה
(בקונסול, פעם אחת) ולהריץ את הסריקה. לחלופין, להמיר ל-CSV ולהשתמש
ב-`scripts/import-catalog.mjs` עבור לקוחות/אתרים.

## סדר מעבר מומלץ

1. להקים פרויקט Supabase ולהריץ `supabase db push` (או
   `node scripts/migrate.mjs`).
2. ליצור ארגון ומשתמש מנהל (ראו README → "הקמה ראשונית").
3. לטעון נספח א׳ ומאגר תכשירים ממקור מאומת.
4. להגדיר לקוחות ואתרים קבועים (או לתת לייבוא ליצור אותם מהיומנים).
5. לייבא את הנתונים מ-localStorage, לעבור על התצוגה המקדימה ולייבא.
6. לעבור על הטיוטות שיובאו, להשלים שדות חסרים, ולהשלים מה שצריך.
7. לשמור את קובץ ה-HTML המקורי ואת גיבוי ה-`localStorage` **לפחות שלוש
   שנים** — נתונים שיובאו כטיוטות אינם תחליף לתיעוד המקורי.

## התאמה למקור, כשקובץ ה-HTML יימסר

1. לפתוח את `pest-log.html` ולתעד: צבעים מדויקים
   (`#...`), גופן, כותרות השלבים והסדר שלהם, שמות השדות והתוויות, וסדר
   המקטעים.
2. **צבעים וגופן:** `src/styles/theme.css` — כל הצבעים הם משתני CSS
   ב-`:root` (`--gold`, `--bg`, ...). שינוי שם מספיק.
3. **כותרות וסדר השלבים:** `WIZARD_STEPS` ב-`src/schema/fieldRegistry.ts`
   + סדר הרכיבים ב-`src/features/wizard/WizardPage.tsx`.
4. **תוויות שדות:** התוויות מוגדרות פעמיים במתכוון — ב-`PATTERNS`
   ב-`fieldRegistry.ts` (לרשימת השדות החסרים) וב-prop `label` של הרכיב.
   יש לעדכן בשניהם; בדיקת `tests/unit/schema.test.ts` → "מיפוי שדות
   לשלבים ולסעיפים" תתפוס אי-התאמה בנתיבים.
5. **מפתחות ה-localStorage בפועל:** להוסיף את שמות המפתחות האמיתיים
   ל-`FIELD_ALIASES` וב-`LEGACY_KEY_PATTERN` ב-
   `src/features/legacyImport/parseLegacy.ts`, ולהוסיף בדיקה
   ב-`tests/unit/legacyImport.test.ts` עם דוגמה אמיתית (בלי פרטי לקוחות
   אמיתיים).
6. להריץ `npm run test:all` ו-`npm run test:e2e`.

**מה לא לשנות בהתאמה לעיצוב:** כללי הוולידציה, חובת האישור המפורש
לאזהרות, נעילת יומן שהושלם, והמספור העוקב. אלה דרישות תוכן, לא עיצוב.
